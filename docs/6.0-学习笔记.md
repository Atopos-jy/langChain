## 二、为什么 LLM 需要记忆系统？

LLM **每次调用都是无状态的**——它不记得上一次说过什么。

```
用户：我叫张三
AI：你好张三！          ← LLM 记住了

用户（新的一次调用）：我叫什么名字？
AI：我不知道啊          ← LLM 忘了！因为没有传入之前的对话
```

所以需要我们在外部维护一个"记忆系统"，每次调用时把相关历史拼进去。

## 三、四种记忆策略总览

```
信息保留：  少 ────────────────────────────→ 多
Token消耗： 少 ────────────────────────────→ 多
实现难度：  低 ────────────────────────────→ 高

Window      Summary        Vector        Buffer
(滑动窗口)  (摘要压缩)     (语义检索)    (全部保留)
```

| 策略 | 保存方式 | 给 LLM 的内容 | Token 消耗 | 信息保留 |
| --- | --- | --- | --- | --- |
| **Buffer** | 全部消息 | 全部历史 | 📈 线性增长 | ✅ 完整 |
| **Window** | 最近 K 轮 | 最近 K 轮（2K 条） | 📊 固定上限 | ❌ 早期丢失 |
| **Summary** | 摘要 + 近期 | 压缩摘要 + 最近几轮 | 📉 缓慢增长 | ✅ 关键信息 |
| **Vector** | 向量库 | 语义检索结果 | 📉 按需召回 | ✅ 相关历史 |

## 四、各案例分析

### 4.1 Buffer Memory（案例一）

**核心代码：**
```typescript
const chatHistory = new InMemoryChatMessageHistory();

async function chat(userInput: string) {
  await chatHistory.addUserMessage(userInput);
  const history = await chatHistory.getMessages();
  const messages = [systemPrompt, ...history];  // 拼上全部历史
  const response = await llm.invoke(messages);
  await chatHistory.addAIMessage(reply);
}
```

**运行结果：** 5 轮对话后，消息数从 2 → 4 → 6 → 8 → 10 线性增长。

**优点：** 模型能看到完整上下文，不会遗漏信息。  
**缺点：** Token 线性增长，长对话会超上下文窗口。  
**适用：** 短对话、客服单轮会话。

### 4.2 Window Memory（案例二）

**核心代码：**
```typescript
const WINDOW_SIZE = 3;  // 保留最近 3 轮

function getRecentMessages(allMessages, windowSize) {
  const maxMessages = windowSize * 2;  // 每轮 2 条（用户+AI）
  return allMessages.slice(-maxMessages);  // 只取末尾
}
```

**运行结果：**
- 第 1-3 轮：正常记住名字、职业、爱好
- 第 4 轮（问名字）→ **回答了别人的名字？** 不是的，是因为名字相关的消息已经丢出窗口了
- 第 5 轮（问爱好）→ 还记得，因为还在窗口内
- 第 6 轮（问名字）→ ❌ **彻底失忆**，忘了名字

**关键发现：** 窗口滑动后，早期对话被**完全删除**，不是"遗忘"而是"不存在了"。

**优点：** Token 消耗固定可控（本例始终 ≤ 7 条）。  
**缺点：** 早期信息完全丢失，无法回忆窗口外的内容。  
**适用：** 闲聊机器人、不需要长期记忆的场景。

### 4.3 Summary Memory（案例三）

**核心代码：**
```typescript
const SUMMARIZE_THRESHOLD = 6;  // 超 6 条时触发摘要
const RECENT_MESSAGES_TO_KEEP = 4;

if (allHistory.length >= SUMMARIZE_THRESHOLD) {
  const newSummary = await summarizeHistory(oldMessages);
  currentSummary = newSummary;
  // 清空历史，只保留最近几轮
  await chatHistory.clear();
  await chatHistory.addMessages(recentMessages);
}
```

**运行结果：**
- 第 4 轮时触发摘要：`"用户张三，前端工程师，住北京。"` ✅
- 第 5 轮补充爱好：摘要更新为 `"用户张三，前端工程师，住北京，喜欢打篮球和弹吉他。"` ✅
- 第 6 轮（问名字）→ **还记得** `"当然记得！你的名字是张三"` ✅

**关键发现：** 相比 Window Memory，早期关键信息通过摘要得以保留，不会"失忆"。

**优点：** Token 增长缓慢，关键信息保留。  
**缺点：** 细节会丢失，且压缩需要额外 LLM 调用（延迟+成本）。  
**适用：** 长期对话助手、客服系统。

### 4.4 Vector Memory（案例四）

**核心思想：** 将对话向量化存入内存库，用户提问时按**语义相关性**检索，而不是按时间顺序。

**实现流程：**
```
用户输入 → Embedding 向量化 → 在向量库中检索相似记录
       → 找到最相关的 K 条历史 → 拼接后发给 LLM → 回复
```

**当前问题：** 需要 QWEN_API_KEY 配置 embeddings。报错：

## 五、四种策略对比表

| 维度 | Buffer | Window | Summary | Vector |
| --- | --- | --- | --- | --- |
| 实现复杂度 | ⭐ | ⭐ | ⭐⭐ | ⭐⭐⭐⭐ |
| Token 成本 | 高 | 低 | 中 | 中 |
| 早期信息 | ✅ 完整 | ❌ 丢失 | ✅ 关键 | ✅ 相关 |
| 细节保留 | ✅ 完整 | ✅ 近期 | ❌ 有损 | ✅ 片段 |
| 需要额外模型 | 否 | 否 | 是（压缩） | 是（Embedding） |
| 适合场景 | 短对话 | 闲聊 | 长期助手 | 知识检索 |

## 六、常见坑点

### ❌ 坑 1：Window 窗口设太小
窗口 = 3 时，3 轮后的信息就丢了。设大一点可以缓解，但 Token 上限也会增加。

### ❌ 坑 2：Summary 压缩丢失细节
"他说他喜欢打篮球和弹吉他" → 摘要里变成 "有爱好" → 细节丢失。  
**解决**：提示词中明确要求保留关键实体信息。

### ❌ 坑 3：Vector 的 Embedding 需要 API
Embedding 模型需要额外的 API 配置（DeepSeek 暂不支持）。  
**解决**：可用 Qwen 或 OpenAI 的 Embeddings，或使用本地模型。

## 七、核心速记

### 7.1 四种记忆一句话总结

```
Buffer  = 全部历史发给 LLM（简单直接）
Window  = 只留最近 K 轮（Token 可控）
Summary = 旧历史压缩为摘要（关键保留）
Vector  = 语义检索相关历史（按需召回）
```

### 7.2 选择指南

```
对话 < 5 轮     → Buffer（最简单）
对话很长但不需要早期信息 → Window（Token 可控）
需要记住用户信息   → Summary（摘要留存）
需要跨大量历史检索 → Vector（语义召回）
```

### 7.3 关键 API

| API | 用途 |
| --- | --- |
| `InMemoryChatMessageHistory` | 内存中的对话历史存储 |
| `chatHistory.addUserMessage()` | 添加用户消息 |
| `chatHistory.addAIMessage()` | 添加 AI 回复 |
| `chatHistory.getMessages()` | 获取全部历史 |
| `chatHistory.clear()` | 清空历史（Summary 压缩后使用） |
