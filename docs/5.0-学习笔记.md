## 二、核心概念

### 2.1 什么是 Agent（智能代理）

Agent 是一种让 LLM **自主决策**的编程范式——不只是"问一句答一句"，而是给模型工具，让它自己决定"下一步做什么"。

**传统 LLM 调用：**

```
用户输入 → 模型回答（一次调用，结束）
```

**Agent 模式：**

```
用户输入 → 模型思考 → 决定行动 → 执行工具 → 观察结果 → 再思考 → ... → 最终回答
```

### 2.2 ReAct 模式（Reasoning + Acting）

**核心流程：**

```
Thought（思考） →  Action（行动） →  Observation（观察） →  Thought → ... →  Final Answer
```

- **Thought**：模型分析当前情况，决定下一步做什么
- **Action**：模型选择工具并传入参数
- **Observation**：工具执行后的返回结果（由系统填入）
- **Final Answer**：模型认为信息足够后给出的最终回答

### 2.3 Tool Calling（原生工具调用）

LLM API 原生支持的"工具调用"能力，不是通过文本解析实现的。

**关键 API：**

```typescript
const llmWithTools = llm.bindTools(tools);
```

调用时，API 请求会带上工具定义：

```json
{
  "model": "...",
  "tools": [{
    "type": "function",
    "function": {
      "name": "search",
      "description": "搜索网络信息",
      "parameters": { "type": "object", "properties": {...} }
    }
  }]
}
```

模型返回结构化 `tool_calls`，不需要正则解析。

### 2.4 三种 Agent 实现方式对比

| 实现方式         | 核心文件                | 工具调用方式               | 循环控制          | 可靠性      | 代码量   |
| ---------------- | ----------------------- | -------------------------- | ----------------- | ----------- | -------- |
| **手动 ReAct**   | `react-agent.ts`        | Prompt 引导 + 正则解析文本 | 手写 `while` 循环 | ❌ 格式易错 | ~50 行   |
| **Tool Calling** | `tool-calling-agent.ts` | `bindTools` + 结构化返回   | 手写 `for` 循环   | ✅ 可靠     | ~30 行   |
| **createAgent**  | `react-agent-plus.ts`   | `createAgent` 封装         | 框架自动处理      | ✅✅        | **3 行** |

### 2.5 手动 ReAct vs Tool Calling（核心区别）

```
手动 ReAct：
  模型输出文本 "Action: search[北京天气]"
  → 你用 /Action:\s*(\w+)\[(.*?)\]/ 正则解析
  → 取出 "search" 和 "北京天气"

Tool Calling：
  模型 API 直接返回：
  { tool_calls: [{ name: "search", args: { query: "北京天气" } }] }
  → 你直接读 toolCall.name 和 toolCall.args
  → 无需解析
```

### 2.6 关键组件

| 组件            | 来源                       | 作用                                |
| --------------- | -------------------------- | ----------------------------------- |
| `tool()`        | `@langchain/core/tools`    | 定义工具（名称、描述、参数 Schema） |
| `bindTools()`   | `ChatOpenAI` 实例方法      | 将工具注册到 LLM（API 级别）        |
| `ToolMessage`   | `@langchain/core/messages` | 工具调用结果的标准消息类型          |
| `createAgent()` | `langchain`                | 官方 Agent 构建函数（封装循环）     |
| `z` (Zod)       | `zod`                      | 声明参数结构，类型安全              |

## 三、代码模板

### 3.1 定义工具（通用模板）

```typescript
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const myTool = tool(
    async ({ param }: { param: string }) => {
        // 工具执行逻辑（查数据库、调 API、算数学……）
        const result = await doSomething(param);
        return result;
    },
    {
        name: "my_tool", // 工具名称（模型用这个名字来调用）
        description: "工具描述，告诉模型什么时候用它", // 模型根据描述选择工具
        schema: z.object({
            // 参数结构（模型按此生成参数）
            param: z.string().describe("参数说明"),
        }),
    },
);
```

### 3.2 Tool Calling Agent（手写循环）

```typescript
const llmWithTools = llm.bindTools([tool1, tool2]);
const messages = [new HumanMessage(question)];

for (let i = 0; i < maxIterations; i++) {
    const response = await llmWithTools.invoke(messages);

    // 没有工具调用 → 有最终答案了
    if (!response.tool_calls || response.tool_calls.length === 0) {
        return response.content;
    }

    messages.push(response);

    for (const toolCall of response.tool_calls) {
        const result = await toolsByName[toolCall.name].invoke(toolCall.args);
        messages.push(
            new ToolMessage({ content: result, tool_call_id: toolCall.id }),
        );
    }
}
```

### 3.3 createAgent（官方封装）

```typescript
import { createAgent } from "langchain";

const agent = createAgent({
    model: llm,
    tools: [searchTool, calculatorTool],
    systemPrompt: "你是一个智能助手，善于使用工具来回答问题。",
});

const result = await agent.invoke({
    messages: [{ role: "user", content: question }],
});

const answer = result.messages[result.messages.length - 1].content;
```

## 四、Plan & Execute（先计划再执行）

### 4.1 概念：ReAct vs Plan & Execute

```
ReAct：
  用户输入 → 思考→行动→观察 → 思考→行动→观察 → ... → 最终答案
           （边走边看，每次只决定下一步）

Plan & Execute：
  用户输入 → 制定完整计划 → 按步骤执行 → 每步评估 → 最终答案
           （先画图纸再施工，全局规划）
```

**什么时候用哪种？**

| 场景 | 推荐模式 | 原因 |
| --- | --- | --- |
| 单步骤问答（"今天天气怎么样？"） | ReAct | 一步到位，不需要规划 |
| 简单多步骤（"搜索X并总结"） | ReAct | 步骤少，走一步看一步够了 |
| 复杂多步骤（"写一份市场分析报告"） | Plan & Execute | 需要全局规划，保证逻辑连贯 |
| 不确定步骤数量的任务 | Plan & Execute | Replanner 可以动态调整计划 |

### 4.2 手写版（plan-and-execute.ts）

三个核心函数：

| 函数 | 角色 | 做了什么 |
| --- | --- | --- |
| `planTask()` | Planner 🧠 | 分析任务 → 输出 JSON steps 数组 |
| `executeStep()` | Executor 🔧 | 执行当前步骤 → 返回结果 |
| `shouldReplan()` | Replanner 🔄 | 评估进度 → 返回 complete/continue |

**主循环逻辑：**

```
planTask() → 获取 steps 数组
while (还有未完成的步骤) {
    executeStep(steps[current]) → 得到结果
    shouldReplan(已完成, 剩余) → 检查是否完成
    if (complete) break
    current++
}
generateSummary() → 最终总结
```

**问题**：搜索工具的字符匹配逻辑太简单，导致大多数搜索命中的都是"北京美食"这一条数据。但 LLM 的推理能力仍然能从有限信息拼出完整答案。

### 4.3 LangGraph 版（plan-and-execute-langgraph.ts）

LangGraph 是 LangChain 的图框架，用**声明式图结构**替代手写循环。

**核心概念对比：**

| 手写版 | LangGraph 版 |
| --- | --- |
| `while` 循环 + `if/else` | `StateGraph` 定义节点和边 |
| 手动管理 `steps`、`completed`、`index` | `Annotation.Root` 自动管理状态 |
| 流程藏在代码逻辑里 | 流程图可视化，一目了然 |
| 条件分支用 `if` | 条件边 `addConditionalEdges` |

**图结构：**

```
[START] → planner → executor → replanner
                                ↗          ↘
                          (继续执行)      (完成) → [END]
```

**关键 API：**

```typescript
import { Annotation, StateGraph, START, END } from "@langchain/langgraph";

// 1. 定义状态（图的共享数据）
const State = Annotation.Root({
  plan: Annotation<string[]>({
    reducer: (_prev, next) => next,  // 合并策略
    default: () => [],
  }),
  completed: Annotation<string[]>({
    reducer: (prev, next) => [...prev, ...next],  // 追加模式
    default: () => [],
  }),
});

// 2. 定义节点（图的处理单元）
async function planNode(state) { /* 返回状态更新 */ }

// 3. 定义条件路由
function shouldContinue(state): "executor" | typeof END { /* ... */ }

// 4. 构建图
const graph = new StateGraph(State)
  .addNode("planner", planNode)
  .addNode("executor", executeNode)
  .addEdge(START, "planner")
  .addConditionalEdges("planner", shouldContinue)
  .compile();

// 5. 执行
const result = await graph.invoke({ task: "..." });
```

### 4.4 Annotation 的 Reducer 机制

LangGraph 的 `Annotation` 定义状态字段时，`reducer` 决定了**多个节点同时更新同一字段时怎么合并**：

```typescript
// 替换模式：新值覆盖旧值
plan: Annotation<string[]>({
  reducer: (_prev, next) => next,  // 直接替换整个 plan
})

// 追加模式：新值追加到旧值后面
completed: Annotation<string[]>({
  reducer: (prev, next) => [...prev, ...next],  // 追加执行结果
})
```

### 4.5 两种实现的输出对比（同一任务）

| 维度 | 手写版 | LangGraph 版 |
| --- | --- | --- |
| 计划步骤数 | 4 步 | 5 步（更细致） |
| 搜索工具命中率 | 所有搜索都只命中"北京美食" | 同样受限，但步骤更细 |
| 最终答案质量 | ✅ 不错 | ✅✅ 更详尽（含美食街、米其林名单） |
| 代码清晰度 | 逻辑直接，容易理解 | 结构更清晰，扩展性好 |
| 状态管理 | 手动变量 | 框架自动维护 |

## 六、常见坑点

### ❌ 坑 1：手动 ReAct 的格式解析失败

模型可能输出 `Action:search[北京天气]`（少空格）或 `Action：搜索[北京天气]`（中文冒号），导致正则 `/Action:\s*(\w+)\[(.*?)\]/` 匹配失败。

**解决方案**：改用 Tool Calling（`bindTools`），不需要解析文本。

### ❌ 坑 2：Tool Calling 不支持所有模型

`bindTools` 依赖模型的 Function Calling 能力。DeepSeek 支持，但一些小型或旧模型可能不支持。

**解决方案**：手动 ReAct 作为 fallback。

### ❌ 坑 3：工具无限循环

Agent 可能一直在调用工具而不给出最终答案。

**解决方案**：设置 `maxIterations` 上限（通常 5-10 步）。

### ❌ 坑 4：ToolMessage 缺少 tool_call_id

```typescript
// ❌ 错误
new ToolMessage({ content: result });

// ✅ 正确
new ToolMessage({ content: result, tool_call_id: toolCall.id });
```

没有 `tool_call_id`，模型无法将工具结果与对应的调用关联起来。

## 十一、核心速记

### 5.1 ReAct vs Plan & Execute 选择

```
简单任务（1-2步）     → ReAct
复杂多步骤任务         → Plan & Execute（先规划再执行）
需要动态调整计划       → Plan & Execute（Replanner 评估）
```

### 5.2 LangGraph 三要素

| 要素 | 对应 API | 作用 |
|------|---------|------|
| **节点** | `.addNode("name", fn)` | 处理单元（Planner / Executor / ...） |
| **边** | `.addEdge(from, to)` | 固定路线 |
| **条件边** | `.addConditionalEdges(from, router)` | 分支/循环决策 |

### 5.3 Annotation 状态管理

```typescript
// 替换模式：新值覆盖旧值
plan: Annotation<string[]>({
  reducer: (_prev, next) => next,
})

// 追加模式：新值追加到旧值后面
completed: Annotation<string[]>({
  reducer: (prev, next) => [...prev, ...next],
})
```

### 5.4 条件路由

路由器函数返回值决定流程走向：

```typescript
function router(state): "节点名" | typeof END {
  return "executor";  // 走到 executor 节点
  return END;         // 结束流程
}
```

### 5.5 LangGraph 优势

- **流程可视化** — 图结构一目了然，不用读完整段 while
- **状态自动管理** — Annotation 替你把变量维护好
- **易扩展** — 加节点加边就行，不用改循环逻辑
